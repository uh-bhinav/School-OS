┌─────────────────────────────────────────────────────────────────────────────┐
│  1.1 WHAT IS CP-SAT?                                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  The timetable solver uses Google OR-Tools CP-SAT (Constraint Programming  │
│  with SAT solving). Think of it as a super-smart sudoku solver that can    │
│  handle thousands of rules simultaneously.                                  │
│                                                                             │
│  KEY CONCEPTS:                                                              │
│                                                                             │
│  1. VARIABLES: Things the solver decides                                    │
│     → Should Math be in Period 1 for Class 8A on Monday? (YES/NO)          │
│     → Should Teacher T001 teach Period 3 for Class 10B? (YES/NO)           │
│                                                                             │
│  2. CONSTRAINTS: Rules that MUST be followed (or SHOULD be preferred)       │
│     → T001 cannot be in two places at once (MUST)                           │
│     → Core subjects prefer morning slots (SHOULD)                           │
│                                                                             │
│  3. OBJECTIVE FUNCTION: What the solver tries to minimize                   │
│     → Total penalty score from violated soft constraints                    │
│     → Lower score = better timetable                                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  1.2 DECISION VARIABLES (How the Solver Thinks)                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  The solver creates BINARY (YES/NO) variables for every possible           │
│  assignment. These are the building blocks of the timetable.               │
│                                                                             │
│  PRIMARY VARIABLE: X[section][day][period][subject] = 0 or 1               │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  Example variables for Class 8A:                                            │
│                                                                             │
│  X[8A][Mon][1][MATH] = ?    "Is Math scheduled for 8A on Monday Period 1?" │
│  X[8A][Mon][1][ENG]  = ?    "Is English scheduled for 8A on Monday P1?"    │
│  X[8A][Mon][2][MATH] = ?    "Is Math scheduled for 8A on Monday Period 2?" │
│  X[8A][Tue][1][MATH] = ?    "Is Math scheduled for 8A on Tuesday P1?"      │
│  ... and so on for EVERY combination                                       │
│                                                                             │
│  If the solver sets X[8A][Mon][1][MATH] = 1, it means:                      │
│  "Yes, Class 8A has Mathematics in Period 1 on Monday"                      │
│                                                                             │
│  BLOCK START VARIABLES: B[section][subject][day][period] = 0 or 1          │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For subjects requiring consecutive periods (like labs):                    │
│  B[8A][PHY_LAB][Mon][3] = 1 means "Physics Lab block starts at Period 3"   │
│                                                                             │
│  SCALE EXAMPLE:                                                             │
│  ─────────────────────────────────────────────────────────────────────────  │
│  12 sections × 6 days × 8 periods × 15 subjects = 8,640 variables!         │
│  The solver evaluates BILLIONS of combinations to find the best one.       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  1.3 TWO-PHASE SOLVING PIPELINE                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  The solver uses a two-phase approach to GUARANTEE a result:               │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  PHASE 1: FEASIBILITY (Find ANY valid timetable)                    │   │
│  │                                                                     │   │
│  │  • Uses only HARD_CORE constraints (no double-booking, etc.)        │   │
│  │  • Ignores soft constraints completely                              │   │
│  │  • Goal: Just find SOMETHING that works                             │   │
│  │  • If fails: Auto-relaxes constraints in priority order             │   │
│  │                                                                     │   │
│  │  Time: ~40% of total time limit                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                           │                                                 │
│                           ▼                                                 │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  PHASE 2: OPTIMIZATION (Make the timetable GOOD)                    │   │
│  │                                                                     │   │
│  │  • Starts from Phase 1 solution                                     │   │
│  │  • Adds ALL soft constraints with weights                           │   │
│  │  • Goal: Minimize total penalty score                               │   │
│  │  • Returns best solution found (even if time runs out)              │   │
│  │                                                                     │   │
│  │  Time: ~60% of total time limit                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  WHY TWO PHASES?                                                            │
│  • A bad timetable is better than NO timetable                              │
│  • Phase 1 guarantees you get SOMETHING                                     │
│  • Phase 2 improves it as much as time allows                               │
│  • If Phase 2 makes it worse, we return Phase 1 solution                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

              PART 2: INHERENT/CORE CONSTRAINTS (Always Enforced)
================================================================================
================================================================================

These constraints are ALWAYS active and CANNOT be disabled. They represent
the fundamental laws of physics/logic that make a timetable valid.

┌─────────────────────────────────────────────────────────────────────────────┐
│  2.1 NO DOUBLE-BOOKING FOR CLASSES                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  RULE: A class section can only have ONE subject per period                 │
│                                                                             │
│  LOGIC: Class 8A cannot simultaneously have Math AND English in Period 1    │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each section, for each day, for each period:                           │
│                                                                             │
│    SUM(all subjects assigned to this slot) ≤ 1                              │
│                                                                             │
│  Mathematically:                                                            │
│    X[8A][Mon][1][MATH] + X[8A][Mon][1][ENG] + X[8A][Mon][1][SCI] + ... ≤ 1 │
│                                                                             │
│  This means AT MOST one of these can be 1 (true).                           │
│                                                                             │
│  CODE LOCATION: add_section_single_subject_constraint()                     │
│                                                                             │
│  EXAMPLE:                                                                   │
│  ✗ INVALID: 8A has MATH and ENG both in Monday Period 1                    │
│  ✓ VALID:   8A has MATH in Monday Period 1, ENG in Monday Period 2         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  2.2 NO DOUBLE-BOOKING FOR TEACHERS                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  RULE: A teacher can only teach ONE class at any given time                 │
│                                                                             │
│  LOGIC: Teacher T001 cannot teach 8A Math and 9B Math at the same time     │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  Step 1: Build teacher assignment map                                       │
│          T001 → [(8A, MATH), (9A, MATH), (10A, MATH)]                       │
│          T002 → [(8A, ENG), (8B, ENG), (9A, ENG)]                           │
│                                                                             │
│  Step 2: For each teacher, for each time slot:                              │
│          SUM(assignments for this teacher at this time) ≤ 1                 │
│                                                                             │
│  Mathematically for T001 on Monday Period 1:                                │
│    X[8A][Mon][1][MATH] + X[9A][Mon][1][MATH] + X[10A][Mon][1][MATH] ≤ 1    │
│                                                                             │
│  Step 3: Also enforce availability                                          │
│          If T001 is blocked on Monday Period 3:                             │
│          X[8A][Mon][3][MATH] = 0  (forced to false)                         │
│          X[9A][Mon][3][MATH] = 0                                            │
│          X[10A][Mon][3][MATH] = 0                                           │
│                                                                             │
│  CODE LOCATION: add_teacher_single_assignment_constraint()                  │
│                                                                             │
│  EXAMPLE:                                                                   │
│  ✗ INVALID: T001 teaches 8A Math AND 9A Math both on Monday Period 1       │
│  ✓ VALID:   T001 teaches 8A Math on Monday P1, 9A Math on Monday P2        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  2.3 TEACHER CAN TEACH MULTIPLE SUBJECTS                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  RULE: A single teacher CAN be assigned to teach different subjects         │
│        to the same class OR different classes.                              │
│                                                                             │
│  HOW IT WORKS:                                                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  This is NOT a constraint - it's enabled by the data structure.             │
│                                                                             │
│  In the CLASS-SUBJECT-TEACHER MAP, you can have:                            │
│                                                                             │
│  section_id │ subject_id │ teacher_id                                       │
│  ───────────┼────────────┼──────────────                                    │
│  8A         │ SCI        │ T005        ← T005 teaches Science to 8A        │
│  8A         │ PHY_LAB    │ T005        ← T005 ALSO teaches Physics Lab     │
│  9A         │ SCI        │ T005        ← T005 ALSO teaches Science to 9A   │
│                                                                             │
│  The solver sees T005 assigned to:                                          │
│  - (8A, SCI), (8A, PHY_LAB), (9A, SCI)                                      │
│                                                                             │
│  And ensures T005 is never double-booked across ANY of these assignments.  │
│                                                                             │
│  VALIDATION: Teacher must have subject in "subjects_can_teach" list         │
│  If T005.subjects_can_teach = ["SCI", "PHY_LAB", "CHEM_LAB"]               │
│  Then T005 can be assigned to Science, Physics Lab, or Chemistry Lab       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  2.4 TEACHER-SUBJECT-CLASS PERMANENCE (Academic Year Binding)               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  RULE: Once a teacher is assigned to teach a subject to a class,            │
│        that assignment remains for the entire academic year.                │
│                                                                             │
│  HOW IT WORKS:                                                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  This is NOT enforced by the solver - it's enforced by DATA INPUT.          │
│                                                                             │
│  The CLASS-SUBJECT-TEACHER MAP (Sheet 4) defines:                           │
│  "Who teaches what to whom"                                                 │
│                                                                             │
│  section_id │ subject_id │ teacher_id                                       │
│  ───────────┼────────────┼──────────────                                    │
│  8A         │ MATH       │ T001        ← T001 teaches Math to 8A ALL YEAR  │
│                                                                             │
│  The solver NEVER changes this mapping. It only decides WHEN T001           │
│  teaches Math to 8A (which day, which period).                              │
│                                                                             │
│  IMPLICATION:                                                               │
│  - If T001 is sick, you need a SUBSTITUTION mechanism                       │
│  - The timetable generator doesn't rotate teachers                          │
│  - Same teacher teaches same subject to same class throughout the year      │
│                                                                             │
│  CHANGING ASSIGNMENTS:                                                      │
│  To change who teaches what, you must:                                      │
│  1. Update the CLASS-SUBJECT-TEACHER MAP data                               │
│  2. Re-run the timetable generator                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  2.5 SUBJECT FREQUENCY REQUIREMENTS                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  RULE: Each subject must receive its required periods per week              │
│                                                                             │
│  DATA SOURCE: Subject's min_per_week and max_per_week fields               │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For each section, for each subject:                                        │
│    min_per_week ≤ SUM(all periods this subject is scheduled) ≤ max_per_week│
│                                                                             │
│  Example for Math in 8A (min=6, max=6):                                     │
│                                                                             │
│    X[8A][Mon][1][MATH] + X[8A][Mon][2][MATH] + X[8A][Mon][3][MATH] + ...   │
│    + X[8A][Tue][1][MATH] + X[8A][Tue][2][MATH] + ...                       │
│    + X[8A][Sat][4][MATH]                                                   │
│    = total_math_periods                                                     │
│                                                                             │
│    6 ≤ total_math_periods ≤ 6    (must be exactly 6 periods)               │
│                                                                             │
│  CODE LOCATION: add_subject_frequency_constraint()                          │
│                                                                             │
│  WHY min AND max?                                                           │
│  • min_per_week = 5: Subject MUST have at least 5 periods                   │
│  • max_per_week = 6: Subject CAN have up to 6 periods (buffer)              │
│  • This gives solver flexibility to fill remaining slots                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌────────────────────────────────────┬─────────┬───────────────────────┐  │
│  │ Constraint                         │ Type    │ Priority/Weight       │  │
│  ├────────────────────────────────────┼─────────┼───────────────────────┤  │

│  │ Substitution Reserve               │ HARD    │ Priority 1 (1st)      │  │
│  │ Max Consecutive Periods            │ HARD    │ Priority 2            │  │
│  │ Teacher Daily Load Limits          │ HARD    │ Priority 3            │  │
│  │ Teacher Weekly Balance             │ HARD    │ Priority 4            │  │
│  │ Block Period Integrity             │ HARD    │ Priority 5            │  │
│  │ Language Block Synchronization     │ HARD    │ Priority 99 (LAST!)   │  │
│  │ Class Teacher in Period 1          │ SOFT    │ Weight 6              │  │
│  │ No Subject Twice Daily             │ SOFT    │ Weight 4              │  │
│  │ Core Subjects in Morning           │ SOFT    │ Weight 3              │  │
│  │ Resource Capacity Limits           │ SOFT    │ Weight 5              │  │
│  └────────────────────────────────────┴─────────┴───────────────────────┘  │
│                                                                             │
│  RELAXATION PRIORITY (for HARD constraints):                                │
│  If solver can't find a solution, it automatically relaxes constraints     │
│  in priority order (lowest number first). Language Sync is LAST (99)       │
│  because it's CRITICAL for Indian schools with language groupings.         │
│                                                                             │
│  SOFT CONSTRAINTS (Moved from HARD for flexibility):                        │
│  - Class Teacher in Period 1: Now a preference, not a requirement          │
│  - No Subject Twice Daily: Now a preference, not a requirement             │
│  - Core Morning: Now a preference, not a requirement                       │
│  - Resource Capacity: Now soft limits with penalties                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.1 LANGUAGE BLOCK SYNCHRONIZATION (STRICT)                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ⚠️ THIS IS A CRITICAL CONSTRAINT FOR INDIAN SCHOOLS                        │
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Ensures all language teachers for the SAME TIER (1st/2nd/3rd language)    │
│  are scheduled SIMULTANEOUSLY so students can split into language groups.   │
│                                                                             │
│  LANGUAGE TIERS (Indian School System):                                     │
│  ─────────────────────────────────────────────────────────────────────────  │
│  • Tier 1 (First Language): Often English (fixed for all students)          │
│  • Tier 2 (Second Language): Options like Kannada, Hindi, Sanskrit          │
│  • Tier 3 (Third Language): Options like French, German, Hindi, Kannada    │
│                                                                             │
│  HOW IT WORKS:                                                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│  1. Groups sections by grade                                                │
│  2. For each grade, identifies languages by tier                            │
│  3. Creates STRICT synchronization: If section A has Kannada at Period 3,  │
│     then section B MUST have Sanskrit at Period 3 (for same tier)           │
│                                                                             │
│  LANGUAGE TEACHER SPECIALIZATION:                                           │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Language teachers are SPECIALISTS in Indian schools:                       │
│  • A Sanskrit teacher ONLY teaches Sanskrit (never Hindi or Kannada)        │
│  • They MAY teach other non-language subjects (History, Geography, etc.)    │
│  • A single teacher can NEVER teach more than one language                  │
│                                                                             │
│  CONFIG KEY: language_sync_enabled (default: TRUE)                          │
│  CODE: add_strict_language_sync_constraint()                                │
│                                                                             │
│  ⚠️ RELAXATION: This is ONLY relaxed as an ABSOLUTE LAST RESORT.            │
│  If relaxed, students may not be able to split into language groups.        │
│  A detailed warning is displayed when this happens.                         │
│                                                                             │
│  (See PART 4 for complete language block explanation)                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.2 CLASS TEACHER IN PERIOD 1 (NOW SOFT)                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  PREFERS (but doesn't require) class teacher in Period 1 with their class. │
│                                                                             │
│  CHANGE FROM PREVIOUS VERSION:                                              │
│  This was previously a HARD constraint that could cause infeasibility.     │
│  Now it's a SOFT constraint with weight 6 (moderate preference).           │
│                                                                             │
│  The solver will TRY to schedule class teachers in Period 1, but if        │
│  there are conflicts, it will schedule them in other periods instead.      │
│                                                                             │
│  CONFIG KEY: class_teacher_period_1 (default: TRUE)                         │
│  SOFT WEIGHT: 6 (configurable via soft_weights.class_teacher_period_1)      │
│  CODE: add_class_teacher_period_1_soft_preference()                         │                              │
│                                                                             │
│  COMMON ISSUE:                                                              │
│  If class teacher only teaches one subject with few periods, this can      │
│  cause infeasibility (e.g., Art teacher as class teacher = problem).       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.3 NO SUBJECT TWICE DAILY                                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Prevents the same subject from appearing twice on the same day.            │
│  Exception: Lab blocks (which need consecutive periods by design).          │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For each section, for each non-block subject, for each day:               │
│    SUM(all periods for this subject on this day) ≤ 1                        │
│                                                                             │
│  Example for MATH in 8A on Monday:                                          │
│    X[8A][Mon][1][MATH] + X[8A][Mon][2][MATH] + ... + X[8A][Mon][8][MATH] ≤ 1│
│                                                                             │
│  EXEMPTIONS:                                                                │
│  Subjects with requires_block=TRUE are excluded (labs need 2 consecutive). │
│                                                                             │
│  CONFIG KEY: no_subject_twice_daily                                         │
│  CODE: add_no_subject_twice_daily_constraint()                              │
│                                                                             │
│  TRADE-OFF:                                                                 │
│  • PRO: Better distribution, less fatigue for students                      │
│  • CON: Harder to schedule subjects with many periods per week              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.4 CORE SUBJECTS IN MORNING (Hard Constraint Mode)                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  When enabled as HARD constraint, forces core subjects (Math, Science,      │
│  English, Social Studies) to be scheduled before lunch break.               │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For core subjects, forbid assignment to periods after lunch:               │
│    X[section][day][period][core_subject] = 0                                │
│    for all periods where is_after_lunch = TRUE                              │
│                                                                             │
│  NOTE: This is usually used as a SOFT constraint (preference) rather than  │
│  a hard constraint, as strict enforcement can cause infeasibility.          │
│                                                                             │
│  IDENTIFICATION OF CORE SUBJECTS:                                           │
│  Subject category = "core" in the Subjects data                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.5 SUBJECT FREQUENCY BOUNDS                                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Enforces min_per_week and max_per_week for each subject.                   │
│                                                                             │
│  THIS IS A CORE CONSTRAINT - Always enabled, cannot be disabled.            │
│                                                                             │
│  (Same as 2.5 above - included here for completeness)                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.6 TEACHER LOAD BOUNDS                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Enforces min/max periods per day and per week for each teacher.            │
│  Also enforces load BALANCE (max-min daily ≤ variance threshold).           │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • Teacher's min_periods_day, max_periods_day                               │
│  • Teacher's min_periods_week, max_periods_week                             │
│  • Constraint's max_daily_load_variance (default: 3)                        │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  Step 1: Count daily load                                                   │
│          daily_load_Mon = SUM(all T001 assignments on Monday)               │
│          daily_load_Tue = SUM(all T001 assignments on Tuesday)              │
│          ...                                                                │
│                                                                             │
│  Step 2: Enforce daily bounds                                               │
│          daily_load_Mon ≤ max_periods_day (e.g., ≤ 6)                       │
│                                                                             │
│  Step 3: Enforce weekly bounds                                              │
│          SUM(all daily loads) ≥ min_periods_week                            │
│          SUM(all daily loads) ≤ max_periods_week                            │
│                                                                             │
│  Step 4: Enforce balance                                                    │
│          MAX(daily_loads) - MIN(daily_loads) ≤ max_daily_load_variance      │
│          (Prevents 7 periods Mon, 2 periods Tue scenario)                   │
│                                                                             │
│  CONFIG KEY: relax_teacher_daily_load, relax_weekly_balance                 │
│  CODE: add_teacher_load_bounds_constraint()                                 │
│                                                                             │
│  ⚠️ PERIOD 0 (assembly/prayer) is EXCLUDED from load calculations           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.7 BLOCK PERIOD INTEGRITY                                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Ensures subjects requiring consecutive periods (labs) get contiguous       │
│  slots that DON'T bridge breaks (recess or lunch).                          │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • Subject's requires_block = TRUE                                          │
│  • Subject's block_length (typically 2 for labs)                            │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  Step 1: Identify block start positions                                     │
│          B[8A][PHY_LAB][Mon][3] = 1 means "block starts at Period 3"        │
│                                                                             │
│  Step 2: Validate block can fit                                             │
│          If block_length=2 and trying to start at Period 3:                 │
│          Check that Period 3 and Period 4 exist                             │
│          Check that no recess/lunch between Period 3 and 4                  │
│                                                                             │
│  Step 3: If block starts, all consecutive slots must have subject           │
│          If B[8A][PHY_LAB][Mon][3] = 1:                                     │
│          Then X[8A][Mon][3][PHY_LAB] = 1 AND X[8A][Mon][4][PHY_LAB] = 1     │
│                                                                             │
│  Step 4: Ensure minimum blocks per week                                     │
│          SUM(all block start vars) ≥ blocks_needed                          │
│          (If PHY_LAB needs 2 periods/week, need at least 1 block)           │
│                                                                             │
│  CONFIG KEY: relax_block_periods                                            │
│  CODE: add_block_period_constraint()                                        │
│                                                                             │
│  EXAMPLE:                                                                   │
│  ✗ INVALID: Physics Lab Period 4-5 when lunch is after Period 4            │
│  ✓ VALID:   Physics Lab Period 5-6 (both after lunch, consecutive)         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  3.8 RESOURCE CAPACITY LIMITS                                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Prevents more sections than capacity from using a resource simultaneously. │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • Resource's max_simultaneous_capacity                                     │
│  • Subject's requires_resource = TRUE and resource_type                     │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  Step 1: Map subjects to resources                                          │
│          PHY_LAB → "Physics Lab" resource (capacity 1)                      │
│          PE → "Sports Ground" resource (capacity 3)                         │
│                                                                             │
│  Step 2: For each time slot, count resource usage                           │
│          SUM(all sections using "Physics Lab" at Monday P3) ≤ 1            │
│          SUM(all sections using "Sports Ground" at Monday P7) ≤ 3          │
│                                                                             │
│  CODE: add_resource_capacity_constraint()                                   │
│                                                                             │
│  EXAMPLE:                                                                   │
│  • Physics Lab has capacity 1                                               │
│  • 8A, 9A, 10A all need Physics Lab                                         │
│  • They CANNOT all have Physics Lab at the same time                        │
│  • Solver schedules them in different periods                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  4.1 WHAT IS A LANGUAGE BLOCK? (Indian School Context)                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  INDIAN SCHOOL LANGUAGE STRUCTURE:                                          │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Indian schools typically have a three-language formula:                    │
│                                                                             │
│  TIER 1 (First Language):                                                   │
│    Usually English, fixed for all students in the school.                   │
│    All students attend the same English class.                              │
│                                                                             │
│  TIER 2 (Second Language):                                                  │
│    Students CHOOSE one from options like:                                   │
│    - Kannada (state language)                                               │
│    - Hindi (national language)                                              │
│    - Sanskrit (classical language)                                          │
│    - Tamil, Telugu, Malayalam, etc. (regional languages)                    │
│                                                                             │
│  TIER 3 (Third Language):                                                   │
│    Students CHOOSE one from options like:                                   │
│    - French, German, Spanish (foreign languages)                            │
│    - Hindi (if not taken as second language)                                │
│    - Kannada (if not taken as second language)                              │
│                                                                             │
│  DURING LANGUAGE PERIOD:                                                    │
│  ─────────────────────────────────────────────────────────────────────────  │
│  When a "second language" period is scheduled, the class SPLITS:            │
│  • Kannada group → goes to Kannada teacher                                  │
│  • Hindi group → goes to Hindi teacher                                      │
│  • Sanskrit group → goes to Sanskrit teacher                                │
│                                                                             │
│  This means ALL language teachers for that tier must be FREE simultaneously.│
│                                                                             │
│  VISUAL EXAMPLE:                                                            │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                            │
│  Normal Subject (Math):                                                    │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  Class 8A (all 40 students)  ──────►  T001 (Math Teacher)            │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                            │
│  Language Block (Second Language):                                         │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  8A Hindi group (15)   + 8B Hindi (12)   ──────►  T007 (Hindi)       │  │
│  │  8A Kannada group (15) + 8B Kannada (15) ──────►  T008 (Kannada)     │  │
│  │  8A Sanskrit group (10)+ 8B Sanskrit (13)──────►  T009 (Sanskrit)    │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  ALL THREE happen SIMULTANEOUSLY at the same period across sections.        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  4.2 HOW LANGUAGE BLOCK DATA IS STRUCTURED (New Format)                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  IN SUBJECTS DATA:                                                          │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  subject_id │ name     │ category │ is_language │ language_tier            │
│  ───────────┼──────────┼──────────┼─────────────┼─────────────────────────  │
│  ENGLISH    │ English  │ language │ TRUE        │ 1                        │
│  KANNADA    │ Kannada  │ language │ TRUE        │ 2                        │
│  HINDI      │ Hindi    │ language │ TRUE        │ 2                        │
│  SANSKRIT   │ Sanskrit │ language │ TRUE        │ 2                        │
│  FRENCH     │ French   │ language │ TRUE        │ 3                        │
│                                                                             │
│  language_tier:                                                             │
│    1 = First Language (e.g., English)                                       │
│    2 = Second Language (e.g., Kannada/Hindi/Sanskrit options)               │
│    3 = Third Language (e.g., French/German options)                         │
│                                                                             │
│  IN TEACHERS DATA:                                                          │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  teacher_id │ name        │ is_language_specialist │ primary_language       │
│  ───────────┼─────────────┼────────────────────────┼─────────────────────── │
│  T007       │ Anita Singh │ TRUE                   │ HINDI                  │
│  T008       │ Mohan Gowda │ TRUE                   │ KANNADA                │
│  T009       │ Lakshmi P   │ TRUE                   │ SANSKRIT               │
│                                                                             │
│  is_language_specialist: TRUE means teacher ONLY teaches this language      │
│  (but may teach other NON-language subjects like History, Geography)        │
│                                                                             │
│  IN CLASSES DATA:                                                           │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  section_id │ grade │ language_block_enabled │ language_tier_config         │
│  ───────────┼───────┼────────────────────────┼───────────────────────────── │
│  8A         │ 8     │ TRUE                   │ {"2": ["KANNADA","SANSKRIT"]}│
│  8B         │ 8     │ TRUE                   │ {"2": ["HINDI","KANNADA"]}   │
│                                                                             │
│  language_tier_config: Maps tier number to available language options       │
│  for that section. Sections in same grade with same tier are synchronized. │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  4.3 HOW THE SOLVER HANDLES LANGUAGE BLOCKS (Strict Implementation)         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  APPROACH: STRICT SYNCHRONIZATION (Updated February 2026)                   │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  The solver now implements STRICT language block synchronization:           │
│                                                                             │
│  1. IDENTIFIES LANGUAGE SUBJECTS BY TIER                                    │
│     Scans subjects for is_language=TRUE and language_tier values            │
│     Groups them: Tier 1: [ENGLISH], Tier 2: [KANNADA, HINDI, SANSKRIT]     │
│                                                                             │
│  2. GROUPS SECTIONS BY GRADE                                                │
│     All sections in the same grade share language block timing              │
│     Example: 8A, 8B, 8C all synchronized for Tier 2 languages               │
│                                                                             │
│  3. CREATES LINKING CONSTRAINTS                                             │
│     For sections in same grade with same tier:                              │
│     IF 8A has KANNADA in Period 3, THEN 8B MUST have HINDI in Period 3     │
│                                                                             │
│     Mathematically:                                                         │
│     X[8A][Mon][3][KANNADA] == X[8B][Mon][3][HINDI]                          │
│                                                                             │
│  4. ENFORCES TEACHER SPECIALIZATION                                         │
│     Language teachers teach ONLY ONE language (no cross-teaching)           │
│     A Sanskrit teacher never teaches Hindi or Kannada                       │
│                                                                             │
│  WHY STRICT NOW WORKS:                                                      │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Previous issues with strict sync were caused by:                           │
│  - Other constraints blocking feasibility                                   │
│  - Insufficient language teacher capacity                                   │
│                                                                             │
│  The new implementation:                                                    │
│  - Moves several constraints to SOFT (class teacher P1, no twice daily)    │
│  - Makes language sync the LAST constraint to relax (priority 99)          │
│  - Provides clear error messages if relaxation is needed                   │
│                                                                             │
│  WHAT HAPPENS IF LANGUAGE SYNC IS RELAXED:                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│  1. A detailed WARNING is shown explaining the impact                       │
│  2. Language periods may NOT be synchronized across sections                │
│  3. Students may not be able to split into language groups                  │
│  4. Admin should review teacher assignments and try again                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  4.4 COMMON LANGUAGE BLOCK ISSUES AND SOLUTIONS                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ISSUE 1: Not enough language teachers                                      │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Problem: Only 2 teachers for 3 language options                            │
│  Impact:  Cannot synchronize all languages simultaneously                   │
│  Solution: Hire additional language teachers OR reduce language options    │
│                                                                             │
│  ISSUE 2: Language teacher also teaches other subjects                      │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Problem: T007 teaches Hindi AND History AND Geography                      │
│  Impact:  When T007 has History, Hindi block cannot happen                  │
│  Solution: Limit non-language subjects for language teachers               │
│            Ensure non-language subjects don't conflict with language slots │
│                                                                             │
│  ISSUE 3: Teacher availability conflicts                                    │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Problem: T008 (Kannada) is unavailable Tuesday, but T009 (Sanskrit) is    │
│  Impact:  Cannot synchronize Kannada and Sanskrit on Tuesday               │
│  Solution: Ensure all language teachers have matching availability         │
│                                                                             │
│  ISSUE 4: Unequal section counts across languages                           │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Problem: T007 (Hindi) teaches 2 sections, T009 (Sanskrit) teaches 6       │
│  Impact:  Load imbalance makes synchronization difficult                   │
│  Solution: Balance language teacher assignments across sections             │
│                                                                             │
│  ISSUE 5: Missing language tier configuration                               │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Problem: language_tier not set on subjects                                 │
│  Impact:  Solver auto-detects tier from name (may be wrong)                │
│  Solution: Explicitly set language_tier for all language subjects          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  5.1 WHAT ARE SOFT CONSTRAINTS?                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  HARD constraints MUST be satisfied or the solver fails.                    │
│  SOFT constraints are PREFERENCES that the solver TRIES to satisfy.         │
│                                                                             │
│  If a soft constraint is violated, the timetable is still VALID,           │
│  it just has a higher "penalty score" (less optimal).                       │
│                                                                             │
│  EXAMPLE:                                                                   │
│  "Core subjects should be in the morning" = SOFT constraint                 │
│  → If Math is scheduled after lunch, timetable is still valid              │
│  → But the solver PREFERS morning slots for Math                            │
│  → If forced to choose, it might put Math after lunch                       │
│                                                                             │
│  OBJECTIVE FUNCTION:                                                        │
│  The solver tries to MINIMIZE the total penalty score.                      │
│  Total Score = Σ(weight × violation_count) for all soft constraints        │
│                                                                             │
│  Lower score = Better timetable                                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  5.2 HOW WEIGHTS WORK                                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  Each soft constraint has a WEIGHT (0-20):                                  │
│  • Weight 0 = Disabled (constraint ignored)                                 │
│  • Weight 1-5 = Low priority (nice to have)                                 │
│  • Weight 6-10 = Medium priority (important)                                │
│  • Weight 11-15 = High priority (very important)                            │
│  • Weight 16-20 = Critical (almost like a hard constraint)                  │
│                                                                             │
│  THE MATH:                                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For each soft constraint violation, the solver adds:                       │
│  penalty = weight × violation_variable                                      │
│                                                                             │
│  Example: "Core Morning Preference" with weight=3                           │
│  If Math is scheduled after lunch 5 times across all sections:             │
│  penalty_contribution = 3 × 5 = 15                                          │
│                                                                             │
│  Example: "Teacher Load Balance" with weight=10                             │
│  If T001 has variance of 4 (7 periods Mon, 3 periods Tue):                 │
│  penalty_contribution = 10 × 4 = 40                                         │
│                                                                             │
│  The solver tries to minimize the SUM of all penalties.                     │
│                                                                             │
│  TRADE-OFFS:                                                                │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Higher weight for A means solver will sacrifice B to satisfy A.            │
│                                                                             │
│  If teacher_balance=10 and core_morning=3:                                  │
│  Solver will put Math after lunch if it helps balance teacher loads,        │
│  because 10 > 3.                                                            │
│                                                                             │
│  If you set core_morning=15:                                                │
│  Now 15 > 10, so solver prioritizes morning Math over teacher balance.     │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  5.3 COMPLETE LIST OF SOFT CONSTRAINTS (Updated February 2026)              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  CONSTRAINTS MOVED FROM HARD TO SOFT (High Priority: 15-20):                │
│  ─────────────────────────────────────────────────────────────────────────  │
│  These were previously hard constraints but now are soft preferences.       │
│  Set their weights high (15-20) if they're important to your school.        │
│                                                                             │

┌─────────────────────────────────────────────────────────────────────────────┐
│  5.4 SWEET SPOT CALCULATION GUIDE                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  🎯 HOW MANY CONSTRAINTS IN EACH WEIGHT RANGE?                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For optimal solver performance and quality results:                        │
│                                                                             │
│  ┌─────────────────┬─────────────┬─────────────────────────────────────────┐│
│  │ Weight Range    │ Recommended │ Purpose                                 ││
│  ├─────────────────┼─────────────┼─────────────────────────────────────────┤│
│  │ 15-20 (High)    │ 2-4 max     │ Critical preferences (moved from hard)  ││
│  │                 │             │ These REALLY matter to your school      ││
│  ├─────────────────┼─────────────┼─────────────────────────────────────────┤│
│  │ 10-15 (Medium)  │ 4-6         │ Important preferences                   ││
│  │                 │             │ Core scheduling quality factors         ││
│  ├─────────────────┼─────────────┼─────────────────────────────────────────┤│
│  │ 5-10 (Low)      │ 5-8         │ Nice-to-have preferences                ││
│  │                 │             │ Improve quality when possible           ││
│  ├─────────────────┼─────────────┼─────────────────────────────────────────┤│
│  │ 0-5 (Minimal)   │ 0-3         │ Rarely matters or disabled              ││
│  │                 │             │ Set to 0 to ignore completely           ││
│  └─────────────────┴─────────────┴─────────────────────────────────────────┘│
│                                                                             │
│  ⚠️ COMMON MISTAKES TO AVOID:                                               │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  ❌ DON'T: Set ALL constraints to 20                                        │
│     → Solver can't distinguish priorities, results in poor optimization     │
│                                                                             │
│  ❌ DON'T: Set more than 4 constraints in the 15-20 range                   │
│     → Too many "critical" preferences conflicts with each other             │
│                                                                             │
│  ❌ DON'T: Set 10+ constraints at the same exact weight                     │
│     → Creates ties that slow down optimization                              │
│                                                                             │
│  ✅ DO: Use the full 0-20 range with varied weights                         │
│  ✅ DO: Keep truly critical preferences (2-3) at 15-20                      │
│  ✅ DO: Spread the rest across 5-15 range                                   │
│                                                                             │
│  EXAMPLE BALANCED CONFIGURATION:                                            │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Weight 18: Resource Capacity (1 constraint)                                │
│  Weight 15: Class Teacher P1, No Subject Twice (2 constraints)              │
│  Weight 12: Core Morning (1 constraint)                                     │
│  Weight 10: Teacher Balance, Minimize Gaps, Subject Distribution (3)        │
│  Weight 8:  Specialist Priority (1 constraint)                              │
│  Weight 5:  Leisure Afternoon, PE preferences, Fair Distribution (4)        │
│  Weight 3:  Thinking Break, Language Spread (2 constraints)                 │
│                                                                             │
│  Total: 14 constraints well-distributed = optimal solver behavior           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  5.5 WEIGHT TUNING GUIDE                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  SCENARIO 1: Teachers complain about uneven workloads                       │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Action: Increase "Teacher Load Balance" weight (10 → 15)                   │
│  Effect: Solver prioritizes even daily distribution                         │
│                                                                             │
│  SCENARIO 2: Students seem tired in morning Math                            │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Action: Decrease "Core Morning Preference" weight (12 → 5)                 │
│  Effect: Solver won't fight as hard to put Math in morning                  │
│                                                                             │
│  SCENARIO 3: Too many gaps in teacher schedules                             │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Action: Increase "Minimize Idle Gaps" weight (10 → 15)                     │
│  Effect: Solver tries harder to give teachers contiguous periods            │
│                                                                             │
│  SCENARIO 4: Art/Music teacher always gets last period                      │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Action: Increase "Fair Slot Distribution" weight (5 → 12)                  │
│  Effect: Undesirable slots spread more evenly across teachers              │
│                                                                             │
│  SCENARIO 5: Sanskrit teacher (1 period/week) often left out                │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Action: Increase "Specialist Priority" weight (8 → 15)                     │
│  Effect: Solver schedules rare subjects first before filling others         │
│                                                                             │
│  GENERAL TIPS:                                                              │
│  • Start with defaults, observe results, adjust gradually                   │
│  • Don't set everything to max weight (cancels out)                         │
│  • Weight 0 = completely disabled (useful for testing)                      │
│  • Max weight (20) = almost like a hard constraint                          │
│                                                                             │

┌─────────────────────────────────────────────────────────────────────────────┐
│  6.4 HOW OVERRIDES ARE APPLIED                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PROCESSING ORDER:                                                          │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  1. PREPROCESS PHASE                                                        │
│     ├── Generate period grid from school config                             │
│     ├── Build teacher availability masks (with overrides applied)           │
│     ├── Build section-subject-teacher mapping (with class overrides)        │
│     └── Validate feasibility                                                │
│                                                                             │
│  2. MODEL BUILD PHASE                                                       │
│     ├── Create decision variables                                           │
│     ├── Apply inherent constraints                                          │
│     ├── Apply hard constraints (from toggles + overrides)                   │
│     └── Apply soft constraints (with weights)                               │
│                                                                             │
│  3. SOLVE PHASE                                                             │
│     ├── Phase 1: Find feasibility                                           │
│     ├── Auto-relax if needed                                                │
│     └── Phase 2: Optimize                                                   │
│                                                                             │
│  OVERRIDE PRIORITY:                                                         │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │

│                                                                             │

┌─────────────────────────────────────────────────────────────────────────────┐
│  7.1 BUILDING THE MODEL                                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  STEP-BY-STEP MODEL BUILD:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  1. INITIALIZE                                                              │
│     model = cp_model.CpModel()  # Empty model                               │
│     variables = {}              # Store all decision variables              │
│     penalties = []              # Track soft constraint penalties           │
│                                                                             │
│  2. CREATE VARIABLES                                                        │
│     For each section:                                                       │
│       For each day:                                                         │
│         For each period:                                                    │
│           For each subject this section has:                                │
│             X[section][day][period][subject] = NewBoolVar(...)              │
│                                                                             │
│     For lab subjects, also create block start variables B[...]              │
│                                                                             │
│  3. ADD HARD CONSTRAINTS                                                    │
│     add_section_single_subject_constraint()    # No class double-book       │
│     add_teacher_single_assignment_constraint() # No teacher double-book     │
│     add_subject_frequency_constraint()         # Subject min/max weekly     │
│     add_resource_capacity_constraint()         # Lab capacity limits        │
│     ... (other hard constraints based on config)                            │
│                                                                             │
│  4. ADD SOFT CONSTRAINTS                                                    │
│     For each enabled soft constraint:                                       │
│       penalties.extend(add_<constraint_name>_preference())                  │
│                                                                             │
│  5. SET OBJECTIVE                                                           │
│     model.Minimize(sum(penalties))                                          │
│                                                                             │
│  CODE LOCATION: TimetableSolver.build_model() in model.py                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  7.2 SOLVING PROCESS                                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT HAPPENS DURING SOLVE:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  1. CP-SAT SOLVER INITIALIZATION                                            │
│     solver = cp_model.CpSolver()                                            │
│     solver.parameters.max_time_in_seconds = time_limit                      │
│                                                                             │
│  2. SEARCH PROCESS                                                          │
│     The solver explores the solution space:                                 │
│     • Propagation: Eliminate obviously impossible assignments               │
│     • Search: Try assigning values to variables                             │
│     • Backtrack: If constraint violated, undo and try different             │
│     • Learning: Remember what doesn't work to avoid repeating               │
│                                                                             │
│  3. SOLUTION STATUS                                                         │
│     OPTIMAL    = Best possible solution found, proven optimal               │
│     FEASIBLE   = Valid solution found, may not be optimal (timeout)         │
│     INFEASIBLE = No solution exists (constraints too tight)                 │
│     UNKNOWN    = Couldn't determine (very rare)                             │
│                                                                             │
│  4. EXTRACT SOLUTION                                                        │
│     For each variable:                                                      │
│       if solver.Value(X[section][day][period][subject]) == 1:               │
│         # This subject is scheduled at this slot                            │
│         add to timetable output                                             │
│                                                                             │
│  SOLVE TIME BREAKDOWN (for 120-second limit):                               │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Phase 1 (Feasibility): ~40% = 48 seconds                                   │
│  Phase 2 (Optimization): ~60% = 72 seconds                                  │
│                                                                             │
│  The solver will return the BEST solution found when time runs out,         │
│  even if it hasn't proven optimality.                                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  7.3 RELAXATION STRATEGY                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  IF PHASE 1 FAILS (No feasible solution):                                   │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  The solver automatically relaxes constraints in priority order:            │
│                                                                             │
│  ITERATION 1: Relax "Language Block Sync" (priority 1)                      │
│  ├── Disable language_sync_constraint()                                     │
│  ├── Try solve again                                                        │
│  └── If still fails → continue to iteration 2                               │
│                                                                             │
│  ITERATION 2: Relax "Class Teacher Period 1" (priority 2)                   │
│  ├── Disable class_teacher_period_1_constraint()                            │
│  ├── Try solve again                                                        │
│  └── If still fails → continue to iteration 3                               │
│                                                                             │
│  ITERATION 3: Relax "No Subject Twice Daily" (priority 3)                   │
│  ... and so on                                                              │
│                                                                             │
│  RELAXATION ORDER (from constraint_types.py):                               │
│  ─────────────────────────────────────────────────────────────────────────  │
│  1. Language Sync         ← First to relax (most restrictive)               │
│  2. Class Teacher P1                                                        │
│  3. No Subject Twice                                                        │
│  4. Core Morning (hard)                                                     │
│  5. Teacher Load Bounds                                                     │
│  6. Block Period Integrity                                                  │
│  7. Max Consecutive       ← Last to relax                                   │
│                                                                             │
│  NEVER RELAXED (HARD_CORE):                                                 │
│  • Teacher single assignment (no double-booking)                            │
│  • Section single subject (no class double-booking)                         │
│  • Subject frequency (min/max periods)                                      │
│  • Resource capacity                                                        │
│                                                                             │
│  If still infeasible after all relaxations:                                 │
│  → Return error with diagnostics                                            │
│  → Usually indicates data problem (not enough teachers, impossible load)    │
│                                                                             │
│  CODE LOCATION: TwoPhaseSolver._solve_with_relaxation()                     │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  8.1 MAX CONSECUTIVE PERIODS (HARD_RELAXABLE)                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Prevents a teacher from teaching more than N consecutive periods           │
│  without a break (recess or lunch).                                         │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • constraints_config.max_consecutive_default (default: 3)                  │
│  • Per-teacher override: teacher.max_consecutive_periods                    │
│  • Setting to 99 effectively disables this constraint                       │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For each teacher, for each day:                                            │
│  1. Sort periods in order                                                   │
│  2. Slide a window of size (max_consecutive + 1) across the day             │
│  3. If the window does NOT span a break (recess/lunch):                     │
│       SUM(teacher assignments in window) ≤ max_consecutive                  │
│                                                                             │
│  Example with max_consecutive=3 for Teacher T001 on Monday:                 │
│  Window [P1, P2, P3, P4]: SUM(T001 assignments in P1-P4) ≤ 3              │
│  Window [P2, P3, P4, P5]: SUM(T001 assignments in P2-P5) ≤ 3              │
│                                                                             │
│  If recess falls between P4 and P5, the window [P3,P4,P5,P6] is SKIPPED   │
│  because the break naturally resets the consecutive count.                  │
│                                                                             │
│  CONFIG KEY: max_consecutive_default (set to 99 to disable)                 │
│  RELAXATION PRIORITY: 2 (relaxed early if infeasible)                       │
│  CODE: add_max_consecutive_constraint()                                     │
│                                                                             │
│  EXAMPLE:                                                                   │
│  ✗ INVALID: T001 teaches P1, P2, P3, P4 with no break (max=3)             │
│  ✓ VALID:   T001 teaches P1, P2, P3, free P4, teaches P5                  │
│  ✓ VALID:   T001 teaches P3, P4, [RECESS], P5, P6 (break resets)          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  8.2 SUBSTITUTION RESERVE (HARD_RELAXABLE)                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  At every period throughout the day, ensures at least N teachers            │
│  are UNASSIGNED and free, available as substitutes if a teacher             │
│  is absent.                                                                 │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • constraints_config.substitution_reserve_count (default: 0 = disabled)    │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  For each day, for each period:                                             │
│  1. Create an "is_assigned" indicator for each teacher                      │
│     is_assigned[T] = 1 if teacher T is teaching ANY class this period       │
│  2. Count total assigned teachers:                                          │
│     assigned_count = SUM(is_assigned for all teachers)                      │
│  3. Enforce reserve:                                                        │
│     assigned_count ≤ total_teachers - reserve_count                         │
│                                                                             │
│  Mathematically:                                                            │
│  SUM(is_assigned[T] for all T) ≤ |Teachers| - reserve_count                │
│                                                                             │
│  Example with 20 teachers and reserve_count=2:                              │
│  At most 18 teachers can be assigned at any given period.                   │
│  2 teachers must always be free (for substitution duty).                    │
│                                                                             │
│  CONFIG KEY: substitution_reserve_count (0 = disabled, >0 = enabled)        │
│  RELAXATION PRIORITY: 1 (first to relax - least impactful on quality)       │
│  DEFAULT: Disabled (0)                                                      │
│  CODE: add_substitution_reserve_constraint()                                │
│                                                                             │
│  ⚠️ NOTE: This can significantly restrict the solver, especially in small   │
│  schools with few teachers. Only enable if your school has enough staff.    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  8.3 TEACHER AVAILABILITY / BLOCKED PERIODS (HARD_CORE)                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Prevents the solver from assigning a teacher to ANY class during           │
│  periods when the teacher is unavailable (blocked).                         │
│                                                                             │
│  This is a HARD_CORE constraint - it CANNOT be relaxed or disabled.         │
│  It is enforced INSIDE add_teacher_single_assignment_constraint().          │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • Teacher's availability field (see Part 6.1 for data structure)           │
│  • Processed by build_all_availability_masks() in preprocess.py             │
│                                                                             │
│  HOW SOLVER IMPLEMENTS IT:                                                  │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  Step 1: Build availability mask for each teacher                           │
│          availability_mask[(day, period)] = True/False                       │
│                                                                             │
│  Step 2: For each teacher, for each time slot:                              │
│          If availability_mask[(day, period)] == False:                       │
│              Force ALL assignment variables for this teacher to 0            │
│              X[section][day][period][subject] = 0                            │
│              for ALL (section, subject) pairs this teacher is assigned to   │
│                                                                             │
│  Example: Teacher T001 is blocked on Wednesday:                             │
│  X[8A][Wed][1][MATH] = 0                                                   │
│  X[9A][Wed][1][MATH] = 0                                                   │
│  X[10A][Wed][1][MATH] = 0                                                  │
│  ... (all of T001's assignments on Wednesday forced to 0)                   │
│                                                                             │
│  CODE: Part of add_teacher_single_assignment_constraint()                   │
│  PREPROCESS: build_all_availability_masks() in preprocess.py                │
│                                                                             │
│  IMPACT ON OTHER CONSTRAINTS:                                               │
│  - Can make language sync harder (if language teacher is partially blocked) │
│  - Can make subject frequency harder (if only one teacher for a subject)   │
│  - Reduces the "capacity" of a teacher for load calculations               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  8.4 PRAYER/ASSEMBLY PERIOD EXCLUSION (IMPLICIT CORE)                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Period 0 (prayer/morning assembly) is treated specially:                   │
│  - It IS included in the period grid (variables exist for it)               │
│  - It is EXCLUDED from teacher load calculations                            │
│  - Teachers are "present" during prayer but it doesn't count as teaching   │
│  - The solver creates variables for Period 0 but they're typically          │
│    not assigned any subject (prayer is not a "subject")                     │
│                                                                             │
│  DATA SOURCE:                                                               │
│  • school.prayer_enabled (default: True)                                    │
│  • school.prayer_duration_minutes (default: 15)                             │
│  • Period slots with is_prayer=True or period==0                            │
│                                                                             │
│  HOW IT AFFECTS CONSTRAINTS:                                                │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  1. TEACHER LOAD BOUNDS:                                                    │
│     Period 0 is SKIPPED when counting daily/weekly teaching load.           │
│     Code: "if period == 0 or period_slot.get('is_prayer', False): continue" │
│                                                                             │
│  2. LANGUAGE SYNC:                                                          │
│     Period 0 is SKIPPED for language synchronization.                       │
│     Language blocks don't apply during prayer/assembly.                      │
│                                                                             │
│  3. SUBJECT FREQUENCY:                                                      │
│     Period 0 slots can technically have a subject variable = 1,             │
│     but typically no subject is assigned to prayer time.                    │
│                                                                             │
│  WHY THIS MATTERS:                                                          │
│  If Period 0 were counted toward teacher load, it would inflate their      │
│  daily count by 1 every day, potentially triggering max_periods_day limits │
│  prematurely. The exclusion ensures teaching load only reflects actual     │
│  academic instruction time.                                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  8.5 NO FREE PERIODS / CLASS PERIOD FILLING (POLICY CONSTRAINT)             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Ensures that CLASSES (not teachers) have all academic periods filled       │
│  with scheduled subjects.                                                   │
│                                                                             │
│  CURRENT IMPLEMENTATION: NO-OP (Soft enforcement via subject frequency)     │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  This constraint was previously a hard constraint that over-constrained     │
│  the solver. It has been redesigned as follows:                             │
│                                                                             │
│  1. The subject_frequency_constraint ensures subjects meet their            │
│     min_per_week requirements, which fills most slots.                      │
│  2. The single-subject constraint ensures ≤ 1 subject per period.           │
│  3. Together, these allow proper filling while still permitting             │
│     free/study periods when subject totals don't fill all slots.            │
│                                                                             │
│  IMPORTANT DISTINCTION:                                                     │
│  • CLASSES may have study periods/library time (free periods OK)            │
│  • TEACHERS are EXPECTED to have free periods (for prep, substitution)      │
│                                                                             │
│  CONFIG KEY: no_free_periods (default: False)                               │
│  When enabled: Logs policy but relies on subject frequency for filling      │
│                                                                             │
│  CODE: add_no_free_periods_constraint() - currently a logging-only function │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  8.6 LANGUAGE TEACHER SPECIALIZATION (SUB-CONSTRAINT)                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHAT IT DOES:                                                              │
│  Enforces that a language teacher teaches ONLY ONE language.                │
│  This is a sub-constraint enforced within the language sync system.         │
│                                                                             │
│  RULE: A Sanskrit teacher can teach Sanskrit + non-language subjects         │
│        (like History, Geography), but NEVER Hindi or Kannada.               │
│                                                                             │
│  HOW IT WORKS:                                                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│                                                                             │
│  1. Identifies all language subjects across all tiers                       │
│  2. Builds a mapping: teacher_id → set of language subject_ids              │

│                                                                             │

│    assigns each language teacher to one language.                            │

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.1 CORE MORNING PREFERENCE (SOFT)                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Prefer core subjects (Math, Science, English, Social Studies)     │
│           in morning periods (before lunch).                                │
│                                                                             │
│  IDENTIFICATION: Subject is "core" if subject.category == "core"            │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each section, for each core subject:                                   │
│    For each period AFTER LUNCH:                                             │
│      If core subject is assigned here → penalty += weight                   │
│                                                                             │
│  Mathematically:                                                            │
│  penalty_var = 1 if X[section][day][period][core_subj] == 1                 │
│                AND period.is_after_lunch == True                            │
│  Total penalty += weight × penalty_var                                      │
│                                                                             │
│  DEFAULT WEIGHT: 3                                                          │
│  CONFIG KEY: soft_weights.core_morning                                      │
│  CODE: add_core_morning_preference()                                        │
│                                                                             │
│  EXAMPLE:                                                                   │
│  Weight=3, Math scheduled after lunch 5 times across all sections           │
│  → Penalty contribution = 3 × 5 = 15 added to objective function           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.2 TEACHER LOAD BALANCE PREFERENCE (SOFT)                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Minimize the variance in each teacher's daily teaching load       │
│           across the week. Prevents scenarios like 7 periods Monday,        │
│           2 periods Tuesday.                                                │
│                                                                             │
│  NOTE: This is SEPARATE from the HARD teacher load bounds constraint        │
│  (which enforces absolute min/max). This soft constraint penalizes          │
│  UNEVENNESS even within valid bounds.                                       │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each teacher:                                                          │
│    1. Compute daily_load for each day (count of assigned periods)           │
│    2. Find max_daily_load = MAX(daily_load across all days)                 │
│    3. Find min_daily_load = MIN(daily_load across all days)                 │
│    4. variance = max_daily_load - min_daily_load                            │
│    5. penalty += weight × variance                                          │
│                                                                             │
│  Example: T001 has loads [5, 4, 6, 5, 3, 4] across Mon-Sat                 │
│  max=6, min=3, variance=3                                                   │
│  penalty = weight × 3                                                       │
│                                                                             │
│  DEFAULT WEIGHT: 10                                                         │
│  CONFIG KEY: soft_weights.teacher_balance                                   │
│  CODE: add_teacher_balance_preference()                                     │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.3 MINIMIZE IDLE GAPS PREFERENCE (SOFT)                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Minimize idle (free) periods BETWEEN teaching periods for         │
│           teachers. A "gap" is a free period where the teacher has          │
│           teaching BEFORE and AFTER it.                                     │
│                                                                             │
│  HOW A GAP IS DETECTED:                                                     │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each teacher, for each day, for each INTERNAL period:                  │
│    gap = (teacher teaches in previous period)                               │
│       AND (teacher is FREE in current period)                               │
│       AND (teacher teaches in next period)                                  │
│                                                                             │
│  Example: T001 schedule on Monday: [TEACH, TEACH, FREE, TEACH, TEACH]      │
│  Period 3 (FREE) is a GAP because T001 teaches P2 and P4.                  │
│  Period 5 (FREE) is NOT a gap if T001 doesn't teach P6.                    │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each detected gap:                                                     │
│    is_gap = has_prev AND has_next AND is_free (all boolean indicators)      │
│    penalty += weight × is_gap                                               │
│                                                                             │
│  DEFAULT WEIGHT: 5                                                          │
│  CONFIG KEY: soft_weights.minimize_gaps                                     │
│  CODE: add_minimize_gaps_preference()                                       │
│                                                                             │
│  WHY IT MATTERS:                                                            │
│  Teachers with gaps have "dead time" where they must remain on campus       │
│  but aren't teaching. Minimizing gaps leads to more compact schedules.      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.4 LEISURE AFTERNOON PREFERENCE (SOFT)                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Prefer scheduling leisure subjects (PE, Art, Music, Dance,        │
│           Craft) in AFTERNOON periods rather than morning.                  │
│                                                                             │
│  IDENTIFICATION: Subject is "leisure" if subject.category == "leisure"      │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each section, for each leisure subject:                                │
│    For each MORNING period (period ≤ 3):                                    │
│      If leisure subject is assigned here → penalty += weight                │
│                                                                             │
│  Note: This is the INVERSE of core_morning - it penalizes leisure           │
│  subjects in morning slots, encouraging them to fill afternoon slots.       │
│                                                                             │
│  DEFAULT WEIGHT: 2                                                          │
│  CONFIG KEY: soft_weights.leisure_afternoon                                 │
│  CODE: add_leisure_afternoon_preference()                                   │
│                                                                             │
│  TRADE-OFF WITH CORE MORNING:                                               │
│  These two constraints work together: core subjects get pushed to           │
│  morning, leisure subjects get pushed to afternoon. But if core_morning     │
│  weight is high (12) and leisure_afternoon is low (2), the solver will      │
│  prioritize getting core subjects into morning over pushing leisure out.    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.5 AVOID PE IN PERIOD 1 AND AFTER LUNCH (SOFT)                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Avoid scheduling Physical Education (PE) in two specific          │
│           problematic slots:                                                │
│           1. Period 1 (students arrive and shouldn't start with exercise)   │
│           2. Immediately after lunch (digestion concerns)                   │
│                                                                             │
│  IDENTIFICATION: Subject is PE if:                                          │
│  • subject.name contains "PE" or "PHYSICAL" (case-insensitive)              │
│  • subject.subject_id is "PE" or "PHYSICAL_EDUCATION"                       │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each section, for each PE subject:                                     │
│    If PE assigned to Period 1 → penalty += weight                           │
│    If PE assigned to period with is_after_lunch=True → penalty += weight    │
│                                                                             │
│  So PE in Period 1 gets ONE penalty, and PE after lunch gets ANOTHER.       │
│  Both are independent checks.                                               │
│                                                                             │
│  DEFAULT WEIGHT: 4                                                          │
│  CONFIG KEY: soft_weights.avoid_pe_period_1                                 │
│  CODE: add_avoid_pe_period_1_preference()                                   │
│                                                                             │
│  BEST SLOTS FOR PE:                                                         │
│  Based on this constraint, PE is best in periods 2-4 (morning but not P1)  │
│  or late afternoon (P6+, well after lunch).                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.6 SUBJECT DISTRIBUTION PREFERENCE (SOFT)                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Distribute heavy/core subjects evenly across the week.            │
│           Prevents clustering (e.g., 4 Math periods on Monday).             │
│                                                                             │
│  APPLIES TO: Core subjects (category == "core") with 5+ periods/week       │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For subjects with min_per_week >= 5:                                       │
│    For each day:                                                            │
│      Count assignments of this subject on this day                          │
│      If count > 2:                                                          │
│        excess = count - 2                                                   │
│        penalty += weight × excess                                           │
│                                                                             │
│  Example: Math (6 periods/week) appears 4 times on Monday                   │
│  excess = 4 - 2 = 2                                                         │
│  penalty = weight × 2                                                       │
│                                                                             │
│  The "2" threshold means the solver tolerates up to 2 of the same          │
│  subject per day before penalizing, which accommodates subjects that        │
│  have many periods (6-7/week across 6 days ≈ 1-2 per day).                 │
│                                                                             │
│  DEFAULT WEIGHT: 3                                                          │
│  CONFIG KEY: soft_weights.subject_distribution                              │
│  CODE: add_subject_distribution_preference()                                │
│                                                                             │
│  NOTE: This works alongside no_subject_twice_daily (which penalizes >1),    │
│  but this constraint has a higher threshold (>2) and only applies to       │
│  heavy subjects. They complement each other.                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.7 TEACHER FREE PERIOD PREFERENCE (SOFT)                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Ensure each teacher has at least one free period per day          │
│           for preparation, grading, or coordination.                        │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each teacher, for each day:                                            │
│    Count total teaching periods this day                                    │
│    num_periods = total academic periods in the day                          │
│    If teaching_count >= num_periods:                                        │
│      all_busy = 1 (teacher has NO free period)                              │
│      penalty += weight × all_busy                                           │
│                                                                             │
│  A teacher is "all busy" if they teach EVERY SINGLE period in the day.     │
│  Having even one free period avoids the penalty.                            │
│                                                                             │
│  DEFAULT WEIGHT: 2                                                          │
│  CONFIG KEY: soft_weights.teacher_free_period                               │
│  CODE: add_teacher_free_period_preference()                                 │
│                                                                             │
│  INTERACTION WITH OTHER CONSTRAINTS:                                        │
│  • Works with minimize_gaps to give teachers useful (not scattered) free    │
│    time                                                                     │
│  • Works with teacher_load_bounds which sets absolute max periods/day       │
│  • If max_periods_day < total_periods_in_day, this constraint is            │
│    automatically satisfied (teacher MUST have free periods)                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.8 FAIR UNDESIRABLE SLOT DISTRIBUTION (SOFT)                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Distribute undesirable time slots (last period of each day,       │
│           Friday/Saturday last periods) fairly among teachers so no         │
│           single teacher always gets the "worst" slots.                     │
│                                                                             │
│  WHAT COUNTS AS UNDESIRABLE:                                                │
│  ─────────────────────────────────────────────────────────────────────────  │
│  1. The LAST PERIOD of every day (1× penalty)                               │
│  2. The LAST PERIOD of Friday and Saturday (2× penalty - double-counted)    │
│     These are the worst because students/teachers are least focused.        │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  1. Count undesirable slot assignments per teacher                          │
│  2. Find MAX count across all teachers                                      │
│  3. Find MIN count across all teachers                                      │
│  4. unfairness = MAX - MIN                                                  │
│  5. penalty += weight × unfairness                                          │
│                                                                             │
│  Example:                                                                   │
│  T001 has 5 undesirable slots, T002 has 1 undesirable slot                 │
│  unfairness = 5 - 1 = 4                                                     │
│  penalty = weight × 4                                                       │
│                                                                             │
│  The solver tries to equalize the distribution, not eliminate it.            │
│                                                                             │
│  DEFAULT WEIGHT: 5                                                          │
│  CONFIG KEY: soft_weights.fair_slot_distribution                            │
│  CODE: add_fair_slot_distribution_preference()                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.9 SPECIALIST TEACHER PRIORITY (SOFT)                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Prioritize scheduling for specialist/rare subject teachers        │
│           who typically have few periods per week but teach across           │
│           many sections. Ensures they aren't "squeezed out" by the          │
│           optimizer.                                                        │
│                                                                             │
│  WHO IS A SPECIALIST?                                                       │
│  ─────────────────────────────────────────────────────────────────────────  │
│  A teacher is identified as a specialist if ANY of:                         │
│  • teacher.is_specialist == True                                            │
│  • They teach a subject with is_specialist == True                          │
│  • They teach a subject with category in:                                   │
│    ["language", "arts", "music", "special"]                                 │
│  • They teach a subject whose name contains:                                │
│    "sanskrit", "french", "german", "spanish", "music", "art",              │
│    "dance", "craft", "drawing", "painting", "instrumental"                  │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each specialist teacher:                                               │
│    1. Calculate total_required = SUM(min_per_week for each specialist       │
│       subject × section count)                                              │
│    2. Count actual_scheduled = SUM(assignment variables across all slots)   │
│    3. shortfall = total_required - actual_scheduled                         │
│    4. penalty += weight × shortfall                                         │
│                                                                             │
│  Example: Sanskrit teacher needs 12 periods across 6 sections               │
│  If only 10 periods get scheduled: shortfall = 2                            │
│  penalty = weight × 2                                                       │
│                                                                             │
│  DEFAULT WEIGHT: 8                                                          │
│  CONFIG KEY: soft_weights.specialist_priority                               │
│  CODE: add_specialist_teacher_priority()                                    │
│                                                                             │
│  WHY HIGH DEFAULT WEIGHT (8)?                                               │
│  Specialist subjects often have very few periods (1-2/week per section).   │
│  Without prioritization, the solver may "sacrifice" these periods to        │
│  optimize other constraints. A higher weight ensures specialists get        │
│  their minimum periods scheduled reliably.                                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.10 CLASS TEACHER PERIOD 1 - SOFT VERSION (SOFT)                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Prefer (but don't require) that the class teacher teaches         │
│           their own section in Period 1 each day.                           │
│                                                                             │
│  BACKGROUND:                                                                │
│  This was previously a HARD constraint (must be satisfied). It was moved    │
│  to SOFT because:                                                           │
│  • Art/Music teachers as class teachers have very few periods → impossible  │
│  • Class teachers who teach only 1 subject can't fill P1 every day         │
│  • This was the #1 cause of infeasibility in Phase 1                        │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each section with a class_teacher_id:                                  │
│    Find all subjects this class teacher teaches to this section             │
│    For each day:                                                            │
│      Get Period 1 variables for those subjects                              │
│      not_in_p1 = 1 if NONE of those subjects are in Period 1               │
│      penalty += weight × not_in_p1                                          │
│                                                                             │
│  DEFAULT WEIGHT: 6                                                          │
│  CONFIG KEY: soft_weights.class_teacher_period_1                            │
│  CODE: add_class_teacher_period_1_soft_preference()                         │
│                                                                             │
│  HARD VERSION STILL EXISTS:                                                 │
│  The original hard constraint (add_class_teacher_period_1_constraint)       │
│  is still in the code but is NOT called by default. It could be invoked    │
│  if a school absolutely requires this to be mandatory.                      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.11 NO SUBJECT TWICE DAILY - SOFT VERSION (SOFT)                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Prefer not scheduling the same non-block subject more than        │
│           once per day per section.                                         │
│                                                                             │
│  EXEMPTIONS: Subjects with requires_block=True are excluded (labs need      │
│              multiple consecutive periods by design).                        │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each section, for each non-block subject, for each day:               │
│    Count assignments of this subject today                                  │
│    If count > 1:                                                            │
│      excess = count - 1                                                     │
│      penalty += weight × excess                                             │
│                                                                             │
│  Example: Math appears 3 times on Monday for section 8A                     │
│  excess = 3 - 1 = 2                                                         │
│  penalty = weight × 2                                                       │
│                                                                             │
│  DEFAULT WEIGHT: 4                                                          │
│  CONFIG KEY: soft_weights.no_subject_twice_daily                            │
│  CODE: add_no_subject_twice_daily_soft_preference()                         │
│                                                                             │
│  HARD VERSION STILL EXISTS:                                                 │
│  The original hard constraint (add_no_subject_twice_daily_constraint)       │
│  uses a strict ≤ 1 per day rule. It is NOT called by default but           │
│  remains available in the codebase.                                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  9.12 RESOURCE CAPACITY - SOFT VERSION (SOFT)                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  PURPOSE: Penalize (but don't prevent) exceeding resource capacity          │
│           limits. This allows the solver to find solutions even when        │
│           resources are tight.                                              │
│                                                                             │
│  APPLIES TO: Subjects with requires_resource=True and resource_type set     │
│  (e.g., Physics Lab, Chemistry Lab, Sports Ground, Computer Lab)            │
│                                                                             │
│  HOW PENALTY IS CALCULATED:                                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  For each resource type, for each time slot:                                │
│    Count sections using this resource at this time                          │
│    If count > capacity:                                                     │
│      excess = count - capacity                                              │
│      penalty += weight × excess                                             │
│                                                                             │
│  Example: Physics Lab (capacity=1), 3 sections want it at Monday P3        │
│  excess = 3 - 1 = 2                                                         │
│  penalty = weight × 2                                                       │
│                                                                             │
│  DEFAULT WEIGHT: 5                                                          │
│  CONFIG KEY: soft_weights.resource_capacity                                 │
│  CODE: add_resource_capacity_soft_preference()                              │
│                                                                             │
│  HARD VERSION STILL EXISTS:                                                 │
│  add_resource_capacity_constraint() is still in the codebase and enforces  │
│  strict capacity limits. It's registered as HARD_CORE in constraint_types  │
│  but the soft version is now used by default in practice.                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  10.3 THREE-TIER SYSTEM EXPLAINED                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  HARD_CORE: "Laws of physics" - mathematically essential                    │
│  ─────────────────────────────────────────────────────────────────────────  │
│  • Cannot be violated under ANY circumstances                               │
│  • Cannot be disabled via UI or config                                      │
│  • If these can't be satisfied, the problem is genuinely infeasible         │
│  • Example: A teacher literally cannot be in two rooms at once              │
│                                                                             │
│  HARD_RELAXABLE: "School policy" - important but flexible                   │
│  ─────────────────────────────────────────────────────────────────────────  │
│  • Enabled by default but can be auto-relaxed if solver can't find          │
│    feasibility                                                              │
│  • Relaxed in priority order (lowest priority number first)                 │
│  • Each relaxation is logged with a clear warning message                   │
│  • The solver always tries WITHOUT relaxation first                         │
│  • Example: Teacher max consecutive can be relaxed if needed               │
│                                                                             │
│  SOFT: "Preferences" - quality optimization                                 │
│  ─────────────────────────────────────────────────────────────────────────  │
│  • NEVER cause infeasibility (by definition)                                │
│  • Implemented as penalty variables in the objective function               │
│  • Each has a configurable weight (0 = disabled, higher = more important)  │
│  • Solver minimizes total weighted penalty score                            │
│  • Example: We PREFER core subjects in morning but it's not mandatory      │
│                                                                             │
│  PHASE 1 vs PHASE 2:                                                        │
│  • Phase 1: HARD_CORE + HARD_RELAXABLE only (find any valid timetable)     │
│  • Phase 2: All constraints including SOFT (optimize quality)               │
│  • Phase 1 uses ~30% of time, Phase 2 uses ~70% of time                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│  11.1 HOW SUBJECT FREQUENCY WORKS WITH LANGUAGE BLOCKS                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  SPECIAL HANDLING: When language_block_enabled=True for a section,          │
│  the subject frequency constraint for tier-2+ languages uses a special     │
│  "anchor" approach.                                                         │
│                                                                             │
│  THE PROBLEM:                                                               │
│  In a language block, Kannada, Hindi, and Sanskrit all share the SAME      │
│  time slots (they're taught simultaneously to different student groups).    │
│  If we apply frequency constraints independently to each, the solver       │
│  might try to give them different numbers of periods - but they MUST       │
│  have the same count (because they're synchronized).                        │
│                                                                             │
│  THE SOLUTION: Anchor Subject                                               │
│  ─────────────────────────────────────────────────────────────────────────  │
│  1. Group tier-2+ subjects for each section                                 │
│  2. Pick the FIRST subject in the group as the "anchor"                     │
│  3. Apply frequency constraint ONLY to the anchor                           │
│  4. The sync constraint ensures all other subjects in the tier              │
│     automatically get the same number of periods                            │
│                                                                             │
│  Example:                                                                   │
│  Section 8A, Tier 2: [KANNADA, HINDI, SANSKRIT]                             │
│  Anchor: KANNADA                                                            │
│  Frequency constraint: 4 ≤ KANNADA_periods ≤ 5                             │
│  Sync constraint: HINDI_periods == KANNADA_periods                          │
│                   SANSKRIT_periods == KANNADA_periods                        │
│  Result: All three languages get 4-5 periods automatically.                │
│                                                                             │
│  This avoids the solver having 3× the frequency constraints for what       │
│  is essentially one scheduling decision (when does the "language block"    │
│  happen?).                                                                  │
│                                                                             │
│  CODE: Inside add_subject_frequency_constraint() - special branch for      │
│        language_block_enabled sections with tier >= 2                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
